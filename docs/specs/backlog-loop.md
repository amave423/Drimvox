# Спека: список задач и рабочая петля агента

## Зачем

Живой прогон «Неба» (сайт со звёздным небом, DeepSeek v4.1 flash через RouterAI) показал, что нынешний конвейер
медленный и дорогой не из-за модели, а из-за Drimvox. Этап 1 из 4: 2029 вызовов инструментов, из них 223 неудачных,
534 из 730 команд — чтение кода кусками через PowerShell, файл `ui.ts` прочитан 156 раз, 232 млн входных токенов,
около 3,2 часа чистой работы. Причины:

- сжатие истории вырезает файлы, с которыми агент работает: он забывает их, перечитывает кусками и промахивается
  правками; нарезка к тому же ломает кэш провайдера, и каждый шаг оплачивается почти полностью;
- три проверяющих подряд (проверки со скриншотами, приёмщик до трёх кругов, дизайн-ревью), у каждого свои круги;
- опрос раздувает задачу: «красивый серьёзный сайт» превратился в 4 этапа и 212 тестов в первом;
- механизмы-заплатки цепляются друг за друга (защита от пересказов, сторож прогресса, поэтапные проверки).

Цель — работать как хороший агент-программист: одна петля «прочитал → написал → запустил → посмотрел → проверил»,
а человек ведёт работу по списку задач и принимает каждую.

## Цели в цифрах (замер, см. ниже)

- «Небо» до рабочего MVP: не больше 60 минут и ~100 ₽ на DeepSeek v4.1 flash через RouterAI.
- Задача размера S: не больше 15 минут и ~20 ₽.
- Неудачных вызовов инструментов — меньше 5 %.

## Процесс

1. **Опрос** — как сейчас, полный (`docs/specs/quality.md`, `docs/specs/design.md`): круги вопросов, направление
   дизайна, «Хватит».
2. **Список задач.** После опроса агент выдаёт всё, что стоит сделать, одним списком. Первая задача — «MVP:
   минимальная рабочая версия», она собрана из самого необходимого. У каждой задачи: название, что в неё входит
   (2–6 пунктов «готово, когда…»), размер S / M / L и, если есть, от каких задач она зависит.
3. **Выбор.** Пользователь отмечает задачи и ставит порядок. За один заход — не больше **3 очков** (S = 1, M = 2,
   L = 3): одна L, или M + S, или три S. Больше отметить нельзя, Drimvox объясняет почему. Остальное остаётся в списке.
4. **Работа над задачей** — одна петля одного агента (ниже). Задачи из захода идут по одной, по порядку.
5. **Проверка задачи.** Проверки проекта зелёные → один проход проверяющего (ниже). Если проверяющий нашёл
   недоделки — один круг доработки, потом задача всё равно идёт человеку, с честным отчётом.
6. **Ревью человека** после каждой задачи: что сделано, скриншоты (компьютер и телефон, если есть интерфейс),
   изменения, запущенный сайт. Кнопки:
   - «Принять» — задача одним коммитом попадает в папку проекта (на текущую ветку), агент ждёт «Дальше»;
   - «Есть баги» — человек пишет, что не так; агент чинит в той же петле, задача снова приходит на ревью;
   - «Отклонить» — изменения задачи выбрасываются, задача возвращается в список.
7. **Дальше** — следующая задача захода. Когда заход кончился — снова выбор из списка. Список живой: добавить,
   удалить, поменять порядок можно в любой момент; новые задачи можно попросить агента сформулировать из текста.

Режим «Самостоятельно» (без остановок между задачами) остаётся для тех, кто хочет: тогда «Принять» ставит сам
Drimvox после зелёного проверяющего, а человек смотрит итог захода.

## Рабочая петля агента

По образцу проверенных агентов (Claude Code, Aider, OpenCode).

- **Файлы целиком.** `read_file` без ограничения в 2000 строк по умолчанию для файлов до ~1500 строк; агент
  читает файл один раз и держит его. `edit_file` при промахе возвращает не просто ошибку, а актуальный текст
  окрестности (ближайшее похожее место с номерами строк), чтобы следующая правка попала.
- **Команды для кода — не для чтения.** В описании инструментов прямо: читать код — `read_file` и `search`, не
  `Get-Content`/`Select-String`.
- **Размер файлов.** В инструкции агента: файл длиннее ~400 строк дели по ответственности. Проверяющий отмечает
  нарушения.
- **Сжатие истории** заменяется одним редким итогом:
  - порог — доля контекста модели (по каталогу; 60 %, а если контекст неизвестен — 200 тыс. символов);
  - при достижении порога старая часть истории (всё, кроме последних шагов) заменяется кратким итогом, который
    пишет та же модель: что сделано, какие файлы и зачем менялись, что осталось, какие ошибки встречались;
  - после итога агент получает свежие тексты файлов, которые менял в последних шагах (рабочий набор, до ~40 тыс.
    символов);
  - начало истории (системный текст, `AGENTS.md`, задача) не меняется никогда — кэш провайдера работает;
  - нарезка по кусочкам, пересказы в аргументах и защита от них (`refuseCutNotes`) удаляются.
- **Пределы.** На задачу — шаги (по умолчанию 150), время и бюджет. Кончились — задача идёт человеку с тем, что
  сделано, и отчётом «на чём остановился». Без автопродолжения по кругу и без сторожа прогресса: если модель
  застряла, человек видит это на ревью и решает (продолжить, другой моделью, отклонить).
- **Сильная модель** подменяет слабую, если проверки краснеют два раза подряд после «готово» (как сейчас
  `escalate`, но без поэтапных счётчиков).

## Файл контекста `AGENTS.md`

- Живёт в корне проекта; если есть свой `AGENTS.md` или `CLAUDE.md` — Drimvox читает его и дописывает свой раздел
  `## Drimvox` (между маркерами), не трогая остальное.
- Раздел Drimvox: цель проекта в 2–3 строках, решения (стек, стиль, дизайн-бриф коротко), команды запуска и проверок,
  состояние списка задач (сделано / следующая), подводные камни.
- Всегда целиком в начале каждого запроса агента и проверяющего, никогда не сжимается.
- В конце каждой задачи агент обновляет раздел инструментом `update_notes` (полный новый текст раздела, не
  добавка). Предел — 4000 символов; больше — инструмент отказывает и просит сократить.
- Коммитится вместе с задачей.

## Проверяющий

Один проход вместо приёмки в три круга и отдельного дизайн-ревью.

- Отдельный агент (модель приёмки из настроек, иначе сильная, иначе модель задачи), только чтение и команды.
- Получает: `AGENTS.md`, задачу с пунктами «готово, когда…», список изменённых файлов с diff, вывод проверок,
  скриншоты страниц на 1280 и 390 px (Drimvox снимает их сам до запуска проверяющего, по адресам из плана).
- Предел 30 шагов. На 25-м шаге у него остаётся только инструмент вердикта, и он об этом знает заранее.
- Вердикт — по каждому пункту «готово / нет + почему» и общий вид («дизайн по брифу / что поправить»). Вердикт,
  в котором нет всех пунктов, не считается вердиктом: пункт без оценки — «не проверен», а не «не сделан».
- Недоделки → один круг доработки агенту → снова проверки (проверяющий второй раз не ходит, только проверки) →
  ревью человека с отчётом.

## Что остаётся из нынешнего

Копия проекта (worktree) и принятие одним коммитом, разрешения на опасные команды, бюджет, уведомления, экран
ревью, опрос и дизайн-направления, команды и скриншоты, локальные модели, CLI-агенты (для них петля — их
собственная, Drimvox даёт задачу и проверяет результат).

## Что удаляется

Фаза «сначала тесты», спека со строгими требованиями и этапами, круги приёмки (до 3) и дизайн-ревью отдельным
кругом, поэтапные визуальные проверки, сторож прогресса и автопродолжение (`progress.ts`), нарезка истории
(`compact.ts`) и защита от пересказов. Режим команды (оркестратор) остаётся отдельной опцией для независимых задач
из захода; в первой версии — выключен и не переделывается.

## Замер

`scripts/bench.mjs` гоняет эталонные задачи на настоящей модели в отдельной папке данных и пишет таблицу:
задача, сделана ли (проверки + проверяющий), шаги, неудачные вызовы, минуты, ₽.

- **sky** — «Небо», ответы опроса и выбор задачи («MVP») зафиксированы в файле сценария;
- **pomodoro** — маленький сайт-таймер, одна задача S;
- **bugfix** — готовый маленький проект с багом и красным тестом, одна задача S.

Модель — из аргумента (по умолчанию DeepSeek v4.1 flash через RouterAI), ключи — из `.env`. Сначала замер на
нынешнем Drimvox (базовая линия), затем после каждого шага переделки. Результаты — в `docs/bench.md`.

**Записи как тесты.** Переписка настоящей модели из замера сохраняется (без ключей) и проигрывается в юнит-тестах
через поддельного провайдера: регрессии ловятся бесплатно.

## Порядок работы

1. Спека (этот файл), замер на нынешнем Drimvox — базовая линия.
2. Петля: сжатие историей-итогом, инструменты чтения и правки, `AGENTS.md`, пределы. Замер.
3. Проверяющий одним проходом. Замер.
4. Список задач: выдача после опроса, выбор с очками, ревью после каждой задачи, «Есть баги», «Дальше»; новая
   миграция БД для задач списка. Замер.
5. Удаление старого (тесты-сначала, спека-требования, этапы, круги приёмки, сторож, нарезка).
6. Итоговый замер, README, `docs/CONTEXT.md`.

«Готово» на каждом шаге — зелёный `npm run verify` и замер не хуже предыдущего.

## Тесты

- Ядро: петля с поддельной моделью (итог вместо нарезки, рабочий набор после итога, неизменное начало истории),
  `edit_file` с подсказкой при промахе, `update_notes` с пределом, проверяющий с неполным вердиктом, очки захода,
  принятие задачи коммитом в папку, «Есть баги» → доработка → ревью.
- e2e на окне: список задач после опроса, выбор с пределом очков, ревью задачи с «Принять» / «Есть баги» /
  «Дальше», файлы в папке после «Принять».
